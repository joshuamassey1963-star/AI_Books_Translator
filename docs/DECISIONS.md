# Architecture Decision Log

Format: ID · date · decision · why · alternatives · status. Versions checked on pub.dev / Flutter release feed on 2026-11-06.

## D-001 · 2026-11-06 · Flutter + Dart, one UI for Android and iOS
- **Why:** roadmap §7; one codebase, AOT-compiled, Impeller renderer. Native Kotlin/Swift only where needed (OCR, background work, on-device AI).
- **Alternatives:** React Native, Kotlin Multiplatform. Rejected for this team size and roadmap fit.
- **Status:** Accepted.

## D-002 · 2026-11-06 · Pin Flutter stable 3.47.9 (Dart 3.13.7) in CI
- **Why:** reproducible builds; roadmap asks for build-time pinning. It was the current stable on the official release feed on 2026-11-06.
- **Status:** Accepted. Bump only in a dedicated `chore/` commit with CI green.

## D-003 · 2026-11-06 · State management: Riverpod 3 (`flutter_riverpod` 3.4.3, MIT)
- **Why:** compile-safe DI, testable overrides, active (published 2026-09-03). Code generation (`riverpod_generator` 4.0.9) deferred until a feature needs it, to keep Session 1 dependency-light.
- **Alternatives:** Bloc, Provider. Rejected: more boilerplate / less DI power.
- **Status:** Accepted.

## D-004 · 2026-11-06 · Routing: go_router 18.1.3 (BSD-3), StatefulShellRoute.indexedStack
- **Why:** official Flutter package, deep links, per-tab navigation stacks (roadmap §2). Requires Flutter ≥3.44 – satisfied by D-002.
- **Status:** Accepted.

## D-005 · 2026-11-06 · Local data: Drift 2.35.x + SQLite (MIT) — to be added in milestone V1-A
- **Why:** typed queries, migrations with tests, FTS5, transactional checkpoints (roadmap §7).
- **Note:** `sqlite3_flutter_libs` is now `0.6.0+eol`; use `drift_flutter` 0.3.1 / `sqlite3` 3.x native assets instead. Verify on Android + iOS build in V1-A before final.
- **Status:** Proposed (verify in V1-A).

## D-006 · 2026-11-06 · Feature-based clean architecture
- `lib/app` (shell, router, theme) · `lib/core` (shared types, errors, utils) · `lib/features/<feature>/{data,domain,presentation}`.
- Repository pattern between domain and data. Engine components (parser, chunker, glossary, provider adapters, queue, validator, TM, export) live in pure-Dart packages under `lib/features/engine/...` so they are unit-testable without Flutter.
- **Status:** Accepted.

## D-007 · 2026-11-06 · Provider-independent AI layer, BYOK only
- One `TranslationProvider` interface; adapters for Gemini, OpenAI-compatible, OpenRouter, Ollama. Model ids, prices and free-tier claims are never hardcoded; the user enters them and the app tests the connection.
- No shared paid key in the app. Never auto-switch to a paid model.
- **Status:** Accepted (implementation in V1-C).

## D-008 · 2026-11-06 · Honest placeholders
- Unbuilt screens render `PlannedScreen`: status + target version, no buttons, no progress bars, no success messages. Enforced by widget tests.
- **Status:** Accepted.

## D-009 · 2026-11-06 · Open-source reuse policy
- Ideas may be taken from any project; **code** only from permissive licenses (MIT/Apache/BSD) with attribution in `docs/DEPENDENCIES.md`. AGPL/GPL repos (TranslateBooksWithLLMs, Tolmach/book-translator, Ebook-Subtitle-Translator, PapyrusReader) are study-only. No code copied in Session 1.
- **Status:** Accepted.

## D-010 · 2026-11-06 · Branch strategy
- `main` stable (merge only with owner's approval) · `develop` integration · `feature/<id>-<slug>` · `fix/<slug>`. PRs into `develop` with CI required.
- **Status:** Accepted.

## D-011 · 2026-11-06 · Libraries to avoid / re-check
- `epubx` (last release 2023-06) – stale; write our own EPUB parser on `archive` 4.6.0 + `xml` 7.1.0 (both MIT, active) with hardening tests.
- `docx_template` (2023-09) – template-only; DOCX writer to be built on `archive` + OOXML.
- `syncfusion_flutter_pdf` – commercial licence; avoid unless owner approves.
- PDF write: `pdf` 3.13.1 (Apache-2.0); PDF text extraction: evaluate `pdfrx` 2.12.0 (MIT, PDFium) in P0 spike.
- **Status:** Proposed (benchmarks in P0 spike).

## D-012 · 2026-11-06 · Platform folders generated on a CI runner (M1)
- The authoring sandbox cannot run the Flutter SDK, so `android/` + `ios/` were generated by a one-off workflow (`flutter create`, Flutter 3.47.9) that pushed to a review branch; reviewed, fast-forwarded into `develop` (a552f0f), workflow then removed.
- IDs: Android `com.aibooktranslator.ai_book_translator`, iOS `com.aibooktranslator.aiBookTranslator`, display name "AI Book Translator". iOS min 15.0; Android min/target SDK follow Flutter defaults. AGP 9.1.0, Kotlin 2.4.0, Gradle 9.3.1, Java 17 target (CI JDK 21).
- Final store IDs must be confirmed by the owner before the V1 release (changing them after publishing is not possible).
- **Status:** Accepted (IDs provisional).

## D-013 · 2026-11-06 · Release signing and permissions deferred
- Android `release` build type still signs with the debug key (template default). Release APKs must not be distributed until a real keystore is set up via CI secrets (V1 release milestone). iOS signing needs an Apple Developer account – CI only does `--no-codesign`.
- Main AndroidManifest has no INTERNET permission yet (debug/profile have it via Flutter). Add it in M6 together with the first network code.
- **Status:** Accepted.

## D-014 · 2026-11-06 · Own EPUB/DOCX/TXT parsers (M2a)
- Implemented on `archive` + `xml` + `crypto` (all permissive), no code copied from other projects. Pure Dart in `lib/features/engine/parser/` so it can run in an isolate later.
- Safety by default: no extraction to disk, entry-name checks, declared-size and ratio limits, `<!ENTITY>`/internal-DOCTYPE refusal, HTML5 named entities decoded.
- TXT is UTF-8 only; other encodings are refused with a clear message instead of guessing (revisit if owner's books need other encodings).
- **Status:** Accepted (spike; structure model grows in M4).

## D-015 · 2026-11-06 · Autoformat helper workflow
- The authoring sandbox cannot run `dart format`. Pushing a `format/<name>` branch runs `.github/workflows/autoformat.yml`, which formats and pushes back to that branch; the result then goes to `feature/*`/`develop`. Never runs on main/develop.
- **Status:** Accepted.

## D-016 · 2026-11-06 · Extraction, legacy conversion, OCR and translation are separate stages
- Each writes its own versioned text layer (L0 raw … L4 edited). Nothing overwrites an earlier layer; the original file is immutable. Reason: the old reader project lost the ability to tell extraction errors from conversion/OCR errors.
- **Status:** Accepted.

## D-017 · 2026-11-06 · Unicode normalization policy
- L0 raw kept byte-for-byte as extracted; L1 and later layers stored in NFC; search, comparison and glossary matching on NFC. ZWJ/ZWNJ preserved.
- **Status:** Accepted (implementation M2b-1c).

## D-018 · 2026-11-06 · Font sourcing and licensing
- Support is measured by test results, not font counts. Only a small license-checked set is bundled; others are system fonts or user-imported. Proprietary fonts (Mangal, Kokila, Nirmala UI, Apple system fonts) are never bundled. Legacy fonts (Kruti Dev, Chanakya, DevLys, Walkman-Chanakya905) are never bundled or rendered – they only identify which conversion table to use.
- Before bundling: license file checked from upstream, added to `assets/fonts/LICENSES/` and DEPENDENCIES.md.
- **Status:** Accepted.

## D-019 · 2026-11-06 · Hindi PDF export engine is undecided
- No engine is production-ready until X01–X10 pass on Android and iOS. M2b-3 compares the `pdf` package with at least one alternative (native platform PDF, HarfBuzz-shaped glyphs, or HTML print). Copy/search fidelity is tested separately from visual correctness.
- **Status:** Open – decide in M2b-3c.

## D-020 · 2026-11-06 · M2b split into five sub-milestones
- M2b-1 PDF + diagnostics, M2b-2 legacy conversion, M2b-3 Hindi PDF export, M2b-4 provider adapter (mocks), M2b-5 real-book regression. Owner request; keeps each session small and testable. M2a code is unchanged.
- **Status:** Accepted.
