# Architecture Decision Log

Format: ID · date · decision · why · alternatives · status. Versions checked on pub.dev / Flutter release feed on 2026-11-06.

## D-001 · 2026-11-06 · Flutter + Dart, one UI for Android and iOS
- **Why:** roadmap §7; one codebase, AOT-compiled, Impeller renderer. Native Kotlin/Swift only where needed (OCR, background work, on-device AI).
- **Alternatives:** React Native, Kotlin Multiplatform. Rejected for this team size and roadmap fit.
- **Status:** Accepted.

## D-002 · 2026-11-06 · Pin Flutter stable 3.47.9 (Dart 3.13.7) in CI
- **Why:** reproducible builds; roadmap asks for build-time pinning. It was the current stable on the official release feed on 2026-11-06.
- **Status:** Accepted. Bump only in a dedicated `chore/` commit with CI green.

## D-003 · 2026-11-06 · State management: Riverpod 3 (`flutter_riverpod` 3.4.3, MIT)
- **Why:** compile-safe DI, testable overrides, active (published 2026-09-03). Code generation (`riverpod_generator` 4.0.9) deferred until a feature needs it, to keep Session 1 dependency-light.
- **Alternatives:** Bloc, Provider. Rejected: more boilerplate / less DI power.
- **Status:** Accepted.

## D-004 · 2026-11-06 · Routing: go_router 18.1.3 (BSD-3), StatefulShellRoute.indexedStack
- **Why:** official Flutter package, deep links, per-tab navigation stacks (roadmap §2). Requires Flutter ≥3.44 – satisfied by D-002.
- **Status:** Accepted.

## D-005 · 2026-11-06 · Local data: Drift 2.35.x + SQLite (MIT) — to be added in milestone V1-A
- **Why:** typed queries, migrations with tests, FTS5, transactional checkpoints (roadmap §7).
- **Note:** `sqlite3_flutter_libs` is now `0.6.0+eol`; use `drift_flutter` 0.3.1 / `sqlite3` 3.x native assets instead. Verify on Android + iOS build in V1-A before final.
- **Status:** Proposed (verify in V1-A).

## D-006 · 2026-11-06 · Feature-based clean architecture
- `lib/app` (shell, router, theme) · `lib/core` (shared types, errors, utils) · `lib/features/<feature>/{data,domain,presentation}`.
- Repository pattern between domain and data. Engine components (parser, chunker, glossary, provider adapters, queue, validator, TM, export) live in pure-Dart packages under `lib/features/engine/...` so they are unit-testable without Flutter.
- **Status:** Accepted.

## D-007 · 2026-11-06 · Provider-independent AI layer, BYOK only
- One `TranslationProvider` interface; adapters for Gemini, OpenAI-compatible, OpenRouter, Ollama. Model ids, prices and free-tier claims are never hardcoded; the user enters them and the app tests the connection.
- No shared paid key in the app. Never auto-switch to a paid model.
- **Status:** Accepted (implementation in V1-C).

## D-008 · 2026-11-06 · Honest placeholders
- Unbuilt screens render `PlannedScreen`: status + target version, no buttons, no progress bars, no success messages. Enforced by widget tests.
- **Status:** Accepted.

## D-009 · 2026-11-06 · Open-source reuse policy
- Ideas may be taken from any project; **code** only from permissive licenses (MIT/Apache/BSD) with attribution in `docs/DEPENDENCIES.md`. AGPL/GPL repos (TranslateBooksWithLLMs, Tolmach/book-translator, Ebook-Subtitle-Translator, PapyrusReader) are study-only. No code copied in Session 1.
- **Status:** Accepted.

## D-010 · 2026-11-06 · Branch strategy
- `main` stable (merge only with owner's approval) · `develop` integration · `feature/<id>-<slug>` · `fix/<slug>`. PRs into `develop` with CI required.
- **Status:** Accepted.

## D-011 · 2026-11-06 · Libraries to avoid / re-check
- `epubx` (last release 2023-06) – stale; write our own EPUB parser on `archive` 4.6.0 + `xml` 7.1.0 (both MIT, active) with hardening tests.

## D-012 · 2026-11-06 · Platform folders generated on a CI runner (M1)
- The authoring sandbox cannot run the Flutter SDK, so `android/` + `ios/` were generated by a one-off workflow (`flutter create`, Flutter 3.47.9) that pushed to a review branch; reviewed, fast-forwarded into `develop` (a552f0f), workflow then removed.
- IDs: Android `com.aibooktranslator.ai_book_translator`, iOS `com.aibooktranslator.aiBookTranslator`, display name "AI Book Translator". iOS min 15.0; Android min/target SDK follow Flutter defaults. AGP 9.1.0, Kotlin 2.4.0, Gradle 9.3.1, Java 17 target (CI JDK 21).
- Final store IDs must be confirmed by the owner before the V1 release (changing them after publishing is not possible).
- **Status:** Accepted (IDs provisional).

## D-013 · 2026-11-06 · Release signing and permissions deferred
- Android `release` build type still signs with the debug key (template default). Release APKs must not be distributed until a real keystore is set up via CI secrets (V1 release milestone). iOS signing needs an Apple Developer account – CI only does `--no-codesign`.
- Main AndroidManifest has no INTERNET permission yet (debug/profile have it via Flutter). Add it in M6 together with the first network code.
- **Status:** Accepted.

## D-014 · 2026-11-06 · Own EPUB/DOCX/TXT parsers (M2a)
- Implemented on `archive` + `xml` + `crypto` (all permissive), no code copied from other projects. Pure Dart in `lib/features/engine/parser/` so it can run in an isolate later.
- Safety by default: no extraction to disk, entry-name checks, declared-size and ratio limits, `<!ENTITY>`/internal-DOCTYPE refusal, HTML5 named entities decoded.
- TXT is UTF-8 only; other encodings are refused with a clear message instead of guessing (revisit if owner's books need other encodings).
- **Status:** Accepted (spike; structure model grows in M4).

## D-015 · 2026-11-06 · Autoformat helper workflow
- The authoring sandbox cannot run `dart format`. Pushing a `format/<name>` branch runs `.github/workflows/autoformat.yml`, which formats and pushes back to that branch; the result then goes to `feature/*`/`develop`. Never runs on main/develop.
- **Status:** Accepted.

## D-016 · 2026-11-06 · Extraction, legacy conversion, OCR and translation are separate stages
- Each writes its own versioned text layer (L0 raw … L4 edited). Nothing overwrites an earlier layer; the original file is immutable. Reason: the old reader project lost the ability to tell extraction errors from conversion/OCR errors.
- **Status:** Accepted.

## D-017 · 2026-11-06 · Unicode normalization policy
- L0 raw kept byte-for-byte as extracted; L1 and later layers stored in NFC; search, comparison and glossary matching on NFC. ZWJ/ZWNJ preserved.
- **Status:** Accepted (implementation M2b-1c).

## D-018 · 2026-11-06 · Font sourcing and licensing
- Support is measured by test results, not font counts. Only a small license-checked set is bundled; others are system fonts or user-imported. Proprietary fonts (Mangal, Kokila, Nirmala UI, Apple system fonts) are never bundled. Legacy fonts (Kruti Dev, Chanakya, DevLys, Walkman-Chanakya905) are never bundled or rendered – they only identify which conversion table to use.
- Before bundling: license file checked from upstream, added to `assets/fonts/LICENSES/` and DEPENDENCIES.md.
- **Status:** Accepted.

## D-019 · 2026-11-06 · Hindi PDF export engine is undecided
- No engine is production-ready until X01–X10 pass on Android and iOS. M2b-3 compares the `pdf` package with at least one alternative (native platform PDF, HarfBuzz-shaped glyphs, or HTML print). Copy/search fidelity is tested separately from visual correctness.
- **Status:** Open – decide in M2b-3c.

## D-020 · 2026-11-06 · M2b split into five sub-milestones
- M2b-1 PDF + diagnostics, M2b-2 legacy conversion, M2b-3 Hindi PDF export, M2b-4 provider adapter (mocks), M2b-5 real-book regression. Owner request; keeps each session small and testable. M2a code is unchanged.
- **Status:** Accepted.

## D-021 · 2026-11-06 · PDF text engine: pdfrx (PDFium) + own structure scanner (M2b-1a)
- **pdfrx 2.12.0 / pdfrx_engine 0.9.1 (MIT, PDFium BSD-3)** gives text fragments with coordinates on Android, iOS and the Linux CI host. Android debug build and iOS unsigned build succeed with it (run 42158726040).
- pdfrx's public API exposes **no font information per run** and **no ToUnicode flag**. PDFium itself has `FPDFText_GetFontInfo` / `FPDFFont_*` (font name, embedded) but calling raw FFI around pdfrx's worker isolate was not attempted in M2b-1a.
- Therefore a small pure-Dart **PdfStructureScanner** reads per-page font dictionaries (BaseFont, subset prefix, FontFile*, ToUnicode, Encoding), image XObjects/inline images and text operators. Fonts are page-level, not per run (documented limitation, `PdfTextRun.fontName == null`).
- Host tests: `flutter test` does not load pdfium_dart's native asset, so CI downloads the same PDFium release and sets `PDFIUM_PATH`.
- **Status:** Accepted for M2b-1a. Re-evaluate per-run fonts (FFI) in M2b-1b.

## D-022 · 2026-11-06 · System-wide translation scope
- Only platform-sanctioned, user-initiated entry points (paste, share, Android PROCESS_TEXT, clipboard on tap, URL). No universal cross-app access is promised; iOS offers less (no PROCESS_TEXT, no overlays, no accessibility reading).
- AccessibilityService is optional V3 only, never required; Google Play demands a Permission Declaration plus separate prominent disclosure and affirmative consent for non-accessibility-tool apps. A policy review is a gate before V2-STR-07 and V3-STR-01.
- No background clipboard reading. Same engine, consent and BYOK rules as book translation.
- **Status:** Accepted (planning).

## D-023 · 2026-11-06 · Read Aloud / TTS architecture
- TTS engine is separate from the translation engine; `TtsEngine` interface with `SystemTtsEngine` (Android TextToSpeech / iOS AVSpeechSynthesizer, evaluated separately) and, in V2, `AiTtsEngine` adapters.
- Reads only validated layers: L2→L1 for source, L4→L3 for translation; never L0, unvalidated OCR or unconverted legacy text.
- Device voice and online AI voice are labelled differently; AI TTS is BYOK, opt-in per provider, never a silent paid switch; keys never in source, logs or exported audio/metadata.
- Candidate packages (flutter_tts, audio_service, audio_session, just_audio – all MIT/Apache) to be re-checked when the milestone starts.
- **Status:** Accepted (planning).

## D-024 · 2026-11-06 · Layout reconstruction and quality gate (M2b-1b)
- Words/lines/paragraphs are rebuilt from PDFium **tight** glyph boxes (`FPDFText_GetCharBox` via pdfrx). Word breaks use extracted whitespace first, then a geometric gap (0.5 × median glyph height). Paragraph break: vertical gap > 1.6 × median line gap (capped at 2 glyph heights) or first-line indent.
- Reading order: one or two columns (gutter between 30–70 % of width, ≤20 % spanning lines, closest to centre). Tables, footnotes, >2 columns, rotated text: not handled yet.
- Header/footer: lines in the top/bottom 8 % repeating on ≥ half the pages (min 2), or bare page numbers → **candidates**, reported, never deleted silently.
- Quality gate: score 0–100 from FFFD, control, PUA, duplicate glyph, ligature, Latin-1 ratios and high/unknown-risk fonts; `pass ≥ 80`, `block < 50` or all pages need OCR, otherwise `warn` (user confirmation). Thresholds are provisional until M2b-5 real-book regression.
- **Per-run font via PDFium FFI (investigated, not implemented):** `pdfium_dart` 0.4.1 binds `FPDFText_GetFontInfo`, `FPDFText_GetFontWeight`, `FPDFText_GetFontSize`, `FPDFTextObj_GetFont`, `FPDFFont_GetBaseFontName`/`GetIsEmbedded`. pdfrx keeps document handles private inside its worker isolate, so per-char font info needs either a second raw PDFium open of the same bytes (own FFI worker, thread-safety via pdfrx's gate) or an upstream pdfrx API. Planned as a separate spike; until then fonts stay page-level (`PdfTextRun.fontName == null`), nothing inferred.
- **Status:** Accepted for M2b-1b.

## D-025 · 2026-11-06 · Text encoding detection and NFC implementation (M2b-1c)
- `EncodingDetector`: BOM decides (UTF-8, UTF-16 LE/BE; UTF-32 refused). No BOM: strict UTF-8 without NUL bytes, else a UTF-16 *suggestion* from the byte pattern (one parity with ≤3 values covering ≥90 % of bytes) → status `needsConfirmation`; `TxtParser`/`BookParser` import it only with an explicit `textEncoding` override. An override that contradicts a BOM is refused.
- Invalid UTF-8, odd-length UTF-16 and unpaired surrogates are refused with byte offset; `preview()` gives a lossy display-only text flagged `lossy`. Original bytes are kept as an unmodifiable copy; decoded text is not normalized.
- `detectFormat` (RC-012): a BOM or a clear UTF-16 pattern is text even with NUL bytes.
- EPUB/DOCX XML parts: BOM-aware decoding; an XML declaration naming a different encoding is refused (EN06).
- NFC via `unorm_dart` (MIT). Never NFKC. Protected spans copied exactly; digits and ZWJ/ZWNJ untouched. Applying NFC to L1 storage waits for the storage milestone (M3).
- **Status:** Accepted.

## D-026 · 2026-11-06 · Kruti Dev 010 converter (M2b-2a)
- Source: SIL International wsresources `KrutiDev010.map` v1.3 (MIT), the TECkit map used by several MIT tools. GPL converter tables (e.g. the long-circulated JS converter some ports mention) are **not** used.
- Port: same 7 passes (nasal reorder, duplicate glyphs, half form + vertical bar, positional/unpacked glyphs, ikar+reph, visual→logical syllable reorder, byte→Unicode). Input runes are mapped to font bytes via Windows-1252/Latin-1.
- Deliberate differences: bytes 140/229/219 not mapped (public tables disagree; reported, not guessed); 162/170 positional variants mapped in all contexts; half C + low r + aakar → full C + low r + aakar; transducer-inserted ZWJ/ZWNJ removed; output NFC.
- Safety: `LegacyFontRegistry` converts only with a confirmed font identity whose normalized name is exactly Kruti Dev 010 (subset prefix and Bold/Italic allowed). Kruti Dev 011 is refused (differs at bytes 145–148). Input with Devanagari is refused (no double conversion). Raw input kept, output separate, unknown characters kept and reported.
- Not in scope: detection of legacy fonts from PDFs (V1-LEG-01), span-level application, confidence score, Chanakya.
- **Status:** Accepted.

## D-027 · 2026-11-06 · Hindi PDF export Engine A result (M2b-3a)
- Tested: Dart `pdf` 3.13.1 (Apache-2.0) with Noto Serif Devanagari Regular/Bold, Noto Serif (Latin/Greek) and Noto Serif Hebrew as fallback (all OFL-1.1, fetched in CI from notofonts.github.io with pinned SHA-256, never committed). Isolated `PdfExportProbe` interface; 13 synthetic cases; checks by poppler 26.01 (pdftoppm, pdftotext, pdffonts) and a HarfBuzz/raqm reference image (Pillow). Run 42203433139.
- Result: the `pdf` package maps code points to glyphs through `cmap` only (its source has Arabic shaping and bidi, no GSUB/GPOS). Devanagari: i-matra drawn after the consonant, no conjuncts, no reph/rakar, no half forms (ZWJ), visible halants inside words, marks not positioned. Hebrew points misplaced. Latin, polytonic Greek (precomposed), digits and punctuation render correctly.
- Text layer: fonts embedded as subsets with ToUnicode; `pdftotext` returns the exact source Unicode for 11/13 cases. p08 loses spaces between punctuation marks; p13 (Hebrew) returns marks in wrong order with extra spaces.
- Decision: Engine A is **rejected for Hindi output**. No workaround (e.g. hand-made reordering) is added, because it would be unverified and would break copy/search. Next: M2b-3b, one shaped alternative (native platform PDF or HarfBuzz-shaped glyph path), chosen with the owner. The probe stays as a regression harness.
- **Status:** Accepted (Engine A rejected for Devanagari).

## D-028 · 2026-11-07 · Shaped Hindi PDF export: engine selection and PoC result (M2b-3b-1)
- Compared (desk study, then one prototype):
  - **Path A – Android native** (`android.graphics.pdf.PdfDocument` + `StaticLayout`; text shaped by Android's Minikin + HarfBuzz, system Noto fonts): no new packages or licences (Android SDK), no native binaries, APK size impact a few KB of Kotlin, one method channel; testable in CI on an Android emulator. iOS needs a separate counterpart (CoreText / `UIGraphicsPDFRenderer`), not evaluated. Unknown before the test: whether the PDF text layer survives shaping.
  - **Path B – HarfBuzz shaping + own glyph PDF writer**: correct shaping (HarfBuzz, MIT) on both platforms with the same code, and full control of the text layer (ToUnicode + `/ActualText` per cluster). Cost: HarfBuzz native builds for each Android ABI and iOS, FFI bindings, our own CID-font subset writer; more maintenance; size impact roughly a few MB (estimate, not measured).
- **Chosen for the PoC: Path A (Engine B, Android only)**, because it was the cheapest way to get real evidence and adds no dependencies. Run [42367039900](https://github.com/joshuamassey1963-star/AI_Books_Translator/actions/runs/42367039900), Android 14 (API 34) emulator, 3 cases.
- Result: **visual PASS 3/3** (agent review vs HarfBuzz/raqm reference with the same emulator fonts NotoSansDevanagari-VF + Roboto; owner check pending). **Unicode text layer FAIL 3/3** (`pdftotext`): `किताब` → `कताब` (i-matra lost); `क्षेत्र` → `े` only; `राष्ट्र धर्म India 123` → `रा धम India 123`. Fonts embedded with ToUnicode; nothing clipped. Overall **PARTIAL 3/3** – not a pass.
- Root cause (likely, inferred from the pattern, not confirmed in Skia source): the Skia PDF backend behind `PdfDocument` maps each glyph back to at most one code point through the font `cmap`; glyphs created by shaping (conjunct ligatures, i-matra variants, reph) have no `cmap` entry and are dropped from ToUnicode, and no `/ActualText` is written.
- Decision: **Engine B as-is is rejected for production Hindi export** (copy/search broken). It stays as a visual reference and regression probe. No text-layer hack is added.
- Unknowns: iOS behaviour; other Android versions/devices; viewers other than poppler (Chrome, Acrobat, Android viewers) not tested.
- Recommended next (M2b-3b-2, needs owner go): **Path B (HarfBuzz-shaped glyphs + own writer with `/ActualText` per syllable cluster)**, verified with the same harness. Alternative to consider: Engine B visuals plus a separately verified text layer – judged riskier (duplicate or misplaced text in extraction).
- **Status:** Accepted (Path A tried; rejected as-is for copy/search; Path B recommended).

## D-029 · 2026-11-07 · Engine C spike: HarfBuzz glyphs + `/ActualText` (M2b-3b-2a)
- Question: can HarfBuzz-shaped glyphs be written to a valid PDF while copy/search returns the original Unicode? One case only: `किताब` (U+0915 U+093F U+0924 U+093E U+092C).
- Architecture (how visual order and logical text are kept apart):
  - HarfBuzz output per glyph: glyph id, cluster, x/y advance, x/y offset. Buffer filled with code points, so cluster = index of the first source code point. For `किताब` (Noto Serif Devanagari Regular, HarfBuzz 15.0.0): glyphs `uni093F.04`(cl 0), `uni0915`(0), `uni0924`(2), `uni093E`(2), `uni092C`(4). The i-matra glyph is drawn **before** क, and त + ा share one cluster. A glyph is therefore not one character.
  - Clusters → source text: cluster i covers code points `[start_i, start_{i+1})` → `कि`, `ता`, `ब`. Non-monotonic clusters (LTR), clusters outside the text, or uncovered code points are rejected.
  - PDF font: Type0 + CIDFontType2, `/Encoding /Identity-H`, `/CIDToGIDMap /Identity` (2-byte code = glyph id), `/W` widths from HarfBuzz advances, font embedded as `FontFile2` (whole file for now, 280,180 bytes; no subsetting).
  - ToUnicode: only glyphs that are the direct `cmap` image of one code point (क त ा ब). The contextual i-matra glyph has no entry.
  - Text: each cluster is wrapped in `/Span <</ActualText <FEFF…>>> BDC … EMC` (UTF-16BE with BOM, ISO 32000-1 §14.9.4); each glyph is placed with its own `Tm` from the HarfBuzz positions; catalog has `/MarkInfo << /Marked true >>`.
- Result, CI run [42373414737](https://github.com/joshuamassey1963-star/AI_Books_Translator/actions/runs/42373414737), poppler pdftotext, qpdf 12.3.2:
  - `c01_kitab` (span per cluster): qpdf --check ok; visual PASS (agent review vs raqm reference, owner check pending); `pdftotext` = exact source code points, no duplicate text; Hindi word found 1/1; font embedded, ToUnicode present. **End-to-end PASS for this one case.**
  - `c01_kitab_run` (one span for the run): same result.
  - `c01_kitab_control` (no `/ActualText`): same visual, `pdftotext` = `कताब` (i-matra lost). This shows `/ActualText` is what restores the text.
- HarfBuzz integration (desk study, nothing built for devices): CI uses uharfbuzz 0.57.0 (Apache-2.0 bindings around HarfBuzz 15.0.0, MIT), pinned; a CI step checks that fresh shaping equals the committed fixture. On devices HarfBuzz is not a public NDK/iOS API, so production needs it bundled: Android `.so` per ABI (arm64-v8a, armeabi-v7a, x86_64) built with the NDK, iOS xcframework; Dart FFI bindings. Size not measured (estimate under ~1–2 MB per ABI). Shaping cannot be done at build time because book text is user content, so runtime FFI is required. Subsetting: `hb-subset` with retain-gids would keep `CIDToGIDMap /Identity` valid – not tried yet.
- Limits: one case; host-side shaping only; only poppler checked (Acrobat, Chrome/pdf.js, Android/iOS viewers not tested); no subsetting; one font, one line, LTR; FontDescriptor metrics are fixed values, not read from the font.
- Decision: the HarfBuzz + `/ActualText` path is **feasible** and stays the candidate. Not production-ready. Next: M2b-3b-2b (3 PoC cases incl. multi-font Latin/digits, subsetting, a second extractor/viewer), only after owner go.
- **Status:** Accepted (spike PASS for 1 case; path continues).

## D-030 · 2026-11-07 · Engine C three cases, subsetting and extractor interoperability (M2b-3b-2b)
- Scope: C01 `किताब`, C02 `क्षेत्र`, C03 `राष्ट्र धर्म India 123` (Devanagari in Noto Serif Devanagari, `India 123` in Noto Serif; both OFL, SHA-256 pinned in `tool/pdf_probe/fonts.sha256`, not in git). Host-side HarfBuzz 15.0.0 (uharfbuzz 0.57.0). Isolated spike writer; no device code.
- Shaping facts (fixtures `test/fixtures/pdf_probe/*.hb.json`, CI re-shapes and must match): C02 = 7 code points → 3 glyphs (`क्ष` ligature + zero-width `े` in cluster 0–4, `त्र` ligature 4–7). C03 = 22 code points → 18 glyphs; reph glyph drawn after `म` in cluster `र्म`; font runs `[0,13)` Devanagari incl. trailing space, `[13,22)` Latin; digits stay U+0031 U+0032 U+0033.
- Writer changes: several fonts (one Type0/CIDFontType2 + FontDescriptor with the font's own bbox/ascent/descent/cap height each), `.notdef` and out-of-range glyph ids refused, font must be a readable sfnt with enough glyphs, `checkActualText` (no nesting, all glyphs inside spans, UTF-16BE+BOM, source exactly once).
- **ToUnicode policy changed to `strict`:** a glyph gets a ToUnicode entry only if every `/ActualText` span drawing it is that one glyph and its text is exactly that code point. Reason: with the S12 policy (every cmap glyph) MuPDF 1.28.6 output `क्षेे त्र` (U+0947 twice) for C02 — it uses ToUnicode of the zero-width e-matra even inside the span. Control `c02_kshetra_control_cmapall` keeps this evidence.
- Subsetting (hb-subset, `RETAIN_GIDS`, glyph set = used glyphs, unicode set = run text for layout closure). Checks per used glyph: same outline points, same advance, composite components present, and re-shaping with the subset gives identical glyphs/positions; a negative self-test (subset missing the e-matra glyph) is detected. Result: all subsets PASS. Font bytes: Devanagari 280,180 → 9,844 (C01), 17,972 (C02), 14,588 (C03); Latin 712,444 → 23,144 (C03). PDF bytes: C01 282,161 → 11,820; C02 281,621 → 19,410; C03 996,904 → 42,007. Subset renders are pixel-identical to full-font renders. None of the 3 cases uses a composite glyph, so the composite check is not exercised yet.
- Results, CI run [42381200825](https://github.com/joshuamassey1963-star/AI_Books_Translator/actions/runs/42381200825) (qpdf 12.3.2; Poppler pdftotext 26.01.0; PyMuPDF 2.1 / MuPDF 1.28.6; pdfjs-dist 4.10.38; PDFium chromium/8125 via pdfrx). Exact = strict equality, only trailing newlines removed:

| PDF | qpdf | visual (agent) | Poppler | MuPDF | PDFium | PDF.js | overall_c |
|---|---|---|---|---|---|---|---|
| C01 / C01 subset | ok | PASS | EXACT | EXACT | DIFF (extra spaces) | DIFF | PASS |
| C02 / C02 subset | ok | PASS | EXACT | EXACT | EXACT | DIFF | PASS |
| C03 / C03 subset | ok | PASS | EXACT | EXACT | DIFF (extra space) | DIFF | PASS |
| C01/C02/C03 `_word` (one span per word) | ok | PASS | EXACT | EXACT | **EXACT** | DIFF | PASS |

- Interoperability findings (not hidden): (1) **PDFium** honours `/ActualText` but adds a space between per-cluster spans when a cluster's first glyph is not its leftmost/pen-start glyph (`कि ता ब`, `रा ष्ट्र`); one span per word removes this in all 3 cases. (2) **PDF.js 4.10.38** ignores `/ActualText` completely and returns glyph-id garbage for shaped glyphs — fails for every Engine C PDF. (3) **MuPDF** duplicates a zero-width mark when ToUnicode maps it (fixed by the strict policy).
- Not tested: interactive search/copy in Chrome, Acrobat, Firefox, Android/iOS viewers; composite glyphs; X03 ZWJ; line wrapping; device HarfBuzz.
- Decision: Engine C stays the candidate. Use **word-level `/ActualText` spans + strict ToUnicode** as the default for the next step (best result: Poppler, MuPDF and PDFium exact on 3/3). PDF.js compatibility is an open problem (needs a different text strategy or is accepted as a known limitation; owner decision). Not production-ready.
- **Status:** Accepted (3/3 PASS on Poppler + MuPDF; PDFium PASS with word spans; PDF.js FAIL).
